# Helper probe: a test client for the 4.2 checks

A command-line stand-in for a foreign or hostile client of the **installed** helper,
for PLAN.md 4.2 items 3–5. It is not part of the app and is never wired into it.

It connects to the helper's Mach service (`eu.dvad.fortivpntray.helper`) over the real XPC
protocol: `build.sh` compiles `AppIdentity.swift` and `HelperTransport.swift` from
`native/Sources/FortiVPNShared` into it, so the protocol and the service name cannot
drift. It calls `version()` and, if asked, `connect()` with the raw bytes of a file. Unlike the
app, it validates nothing first, which is exactly what a hostile process running as you could do.

| File | Purpose |
|---|---|
| `Sources/main.swift` | The probe |
| `build.sh` | Builds `dist/probe-signed` and `dist/probe-adhoc`, writes `dist/samples/oversized.json` (no root) |
| `samples/host-option.json` | `connect` with host `-c/tmp/x` |
| `samples/realm-newline.json` | `connect` with a realm that contains a newline and a second config line |
| `samples/unknown-key.json` | `connect` with an extra `extraArgs` key |
| `dist/samples/oversized.json` | `connect` over the helper's 16 KiB limit (generated by `build.sh`) |

Each sample differs from a valid request in that one way only.

The two builds are the same program, signed differently:

| Build | Signature | Identifier | Expected against a signed-mode helper |
|---|---|---|---|
| `probe-signed` | local identity | `eu.dvad.fortivpntray` | accepted: exactly what the helper requires |
| `probe-adhoc` | ad-hoc | `eu.dvad.fortivpntray` | rejected |

## Output

```
probe version               ACCEPTED: helper <version>, protocol <n>, caller check <mode>
                            or REJECTED: <XPC error>
probe connect <file.json>   the same, then CONNECT REFUSED: <the helper's reason>
```

Exit status: 0 accepted (and for `connect`, the request refused), 1 rejected, 2 no answer,
3 connect accepted, 64 usage. Every sample should be refused, so 3 means a failed check.
If that ever happens, the probe disconnects the session at once and prints
`CONNECT ACCEPTED (unexpected)`.

The helper refuses a bad request before it looks at the session, so the hostile connects
change nothing, even while you are connected. The probe never sends a valid request.

## Build (maintainer)

`probe-signed` must use the same identity as the installed app, because the helper pins that
certificate's leaf. Without `FVT_SIGN_IDENTITY`, only `probe-adhoc` is built.

```bash
security unlock-keychain ~/Library/Keychains/fvt-signing.keychain-db
FVT_SIGN_IDENTITY="FortiVPNTray Local Signing" \
FVT_SIGN_KEYCHAIN="$HOME/Library/Keychains/fvt-signing.keychain-db" \
spikes/helper-probe/build.sh
```

The build prints `probe-signed leaf certificate SHA-1: …`. That value must equal the
`--client-req-leaf` argument of the installed helper. To read it (the plist is world-readable):

```bash
plutil -p /Library/LaunchDaemons/eu.dvad.fortivpntray.helper.plist
```

## The 4.2 checks (maintainer)

Run these from the repository root. Paste each output into PLAN.md under 4.2.

**Item 4: only the signed app identity is accepted** (signed mode only):

```bash
spikes/helper-probe/dist/probe-signed version   # expect ACCEPTED: … caller check signed
spikes/helper-probe/dist/probe-adhoc version    # expect REJECTED: …
```

**Item 3: another user cannot connect.** `nobody` stands in for the second macOS user.
The UID check rejects it before the signature is looked at. `nobody` cannot read your home
folder, so it runs a copy from `/Users/Shared`:

```bash
mkdir -p /Users/Shared/fvt-helper-probe
cp spikes/helper-probe/dist/probe-signed /Users/Shared/fvt-helper-probe/
chmod 755 /Users/Shared/fvt-helper-probe /Users/Shared/fvt-helper-probe/probe-signed
sudo -u nobody /Users/Shared/fvt-helper-probe/probe-signed version   # expect REJECTED: …
rm -r /Users/Shared/fvt-helper-probe
```

For the full item 3, also run `probe-signed version` from a terminal inside a real second
macOS user's login session. Copy it there the same way.

**Item 5: a hostile same-user client is refused.** This uses `probe-signed`, which the
caller check accepts, so only the helper's own validation stands in the way:

```bash
for f in spikes/helper-probe/samples/*.json spikes/helper-probe/dist/samples/oversized.json; do
  spikes/helper-probe/dist/probe-signed connect "$f"; echo "exit $?"
done
```

Expected, after the `ACCEPTED` line each time:

| Sample | Expected |
|---|---|
| `host-option.json` | `CONNECT REFUSED: The host must be a hostname or an IPv4 address.` |
| `realm-newline.json` | `CONNECT REFUSED: The realm must be 1–63 letters, digits, '.', '_' or '-'…` |
| `unknown-key.json` | `CONNECT REFUSED: The connect request is malformed.` |
| `oversized.json` | `CONNECT REFUSED: The connect request is too large.` |

Each one should end with `exit 0`. The realm text ends with ", not starting with '-'." only
on helpers built after task 4.1.

## Checked without the maintainer (agent)

- `build.sh` builds `probe-adhoc` in Swift 6 mode with identifier `eu.dvad.fortivpntray`.
  `probe-signed` was not built, because the agent does not use the signing identity.
- Each sample, read by the helper's own `ConnectRequest(json:)`, is refused with the reason
  in the table above. The same request with only that defect fixed is accepted, so each
  sample tests one thing.
- `probe-adhoc version` against the helper installed on 2026-10-14, which runs in signed
  mode: `REJECTED: Couldn’t communicate with a helper application. (NSCocoaErrorDomain 4097)`,
  exit 1, while the helper process was running. That is item 4's ad-hoc half; the signed half
  needs `probe-signed`.
